# OS-633 — Jerarquía de cargos en Gestión de Cargos

**Domain:** `[BE]` `[REST]` `[GRAPHQL]` `[PAYROLL]` `[WEB-APP]` `[UI]`
**Branch:** `bugfix/OS-633-positions-hierarchy-ui-review`
**Status:** `implemented — pending review`

---

## 1. Objetivo

Hacer visible y administrable, desde la sección **Gestión de Cargos**, la jerarquía de
cargos que ya existía en base de datos (`EmployeePositionSupervisor`) pero que no era ni
visible ni editable desde esa pantalla.

Al terminar este ticket, desde Gestión de Cargos se puede:

1. Ver qué cargo(s) supervisan a cada cargo (columna en tabla, precarga en edición).
2. Crear o editar un cargo asignándole uno o varios cargos supervisores.
3. Persistir la relación en `EmployeePositionSupervisor` (fuente de verdad existente).
4. Confiar en que el backend valida tenant, self-supervision y ciclos — la UI solo ayuda.

## 2. Contexto

Un ticket previo (**OS-550**, "Organigrama de supervisión por cargo") agregó el modelo
`EmployeePositionSupervisor` y lo pobló vía seed para un tenant (`palos-de-lena`), pero
únicamente para resolver un problema puntual de **asistencia**: filtrar el listado de
colaboradores por los cargos subordinados de un supervisor
(`findSubordinatePositionIds`, consumido también por `vacations` para aprobación por
jerarquía). El módulo de **cargos** (`payroll/employee-positions`, pantalla "Gestión de
Cargos") nunca llegó a conocer ni exponer esa relación: ni el controller/resolver, ni los
DTOs, ni el formulario o la tabla del frontend tenían referencia alguna a
`supervisorPositionId`.

Una auditoría previa a este ticket confirmó exactamente eso: la jerarquía existía en BD,
pero "Gestión de Cargos" era una tabla plana sin ninguna forma de crear, ver o editar el
organigrama — la única manera de poblarlo era escribiendo directo en BD vía el seed.
OS-633 cierra esa brecha reutilizando el modelo existente, sin crear una jerarquía
paralela.

## 3. Arquitectura

`EmployeePositionSupervisor` sigue siendo una relación **muchos-a-muchos** entre cargos
(`positionId` → `supervisorPositionId`, ambos con FK a `EmployeePosition`, únicos por
`tenantId`). No es un árbol de padre único: un cargo puede tener más de un supervisor
(igual que en el organigrama real sembrado por OS-550, donde varios cargos reportan a más
de una posición).

```
Frontend (Gestión de Cargos)
  EmployeePositionsListScreen → columna "Supervisor(es)" (CargoTableItem)
  EmployeePositionForm        → Combobox multiselect (@restopsiq/ui) de cargos activos

        │ REST (payrollFetch) / GraphQL
        ▼
Backend (apps/api/src/payroll)
  EmployeePositionsController / EmployeePositionsResolver
        │
  EmployeePositionsService
        │  - validateSupervisorPositionIds(tenantId, positionId?, ids)
        │      1. self-supervision
        │      2. existencia + tenant (findByIds)
        │      3. ciclos (findSubordinatePositionIds)
        ▼
  EmployeePositionsRepository
        │  - findSupervisorsByPositionIds / replaceSupervisors / findSubordinatePositionIds
        ▼
  EmployeePositionSupervisor (Prisma) ← misma tabla que consumen
                                         AttendanceCollaboratorsRepository y
                                         VacationsRepository (OS-550)

Shared: payroll/utils/employee-position-hierarchy.util.ts
  resolveSubordinatePositionIds(prisma, tenantId, positionId) — BFS único,
  usado por los 3 repositorios (payroll, attendance, vacations).
```

## 5. Cambios Backend

- **DTOs**: `CreateEmployeePositionDto` y el `CreateEmployeePositionInput` de GraphQL
  ganan `supervisorPositionIds?: string[]`; `Update*` lo hereda vía `PartialType`.
  `EmployeePositionResponseDto` / `EmployeePositionType` ganan
  `supervisors: { id, title }[]`.
- **Repository**: `findAll`/`findById`/`findByTitle`/`findByIds`/`create`/`update` ahora
  adjuntan los supervisores directos de cada cargo (`findSupervisorsByPositionIds`).
  Métodos nuevos: `findByIds`, `findSubordinatePositionIds`, `replaceSupervisors`
  (delete + create en `$transaction`).
- **Service**: `validateSupervisorPositionIds(tenantId, positionId, ids)` — privado,
  llamado desde `create`/`update`:
  1. **Self-supervision** → `BadRequestException` si algún id === el propio cargo.
  2. **Tenant/existencia** → `findByIds` ya filtra por `tenantId`; cualquier id que no
     aparezca en el resultado (inexistente o de otro tenant) se reporta como inválido
     con `BadRequestException`.
  3. **Ciclos** → se calcula `findSubordinatePositionIds(tenantId, positionId)` (mismo
     BFS de OS-550) **antes** de tocar la tabla; si algún supervisor candidato ya es
     subordinado directo o transitivo del cargo, se rechaza con `ConflictException`
     (cerraría un ciclo). En creación no aplica: un cargo nuevo no tiene subordinados.
  - `update` distingue `undefined` (no tocar supervisores) de `[]` (limpiarlos) — solo
    llama a `replaceSupervisors` cuando el campo viene definido en el payload.
- **Controller/Resolver**: pasan `supervisorPositionIds` tal cual al service; mapean
  `supervisors` en la respuesta.

## 6. Cambios Frontend

- `EmployeePosition` gana `supervisors: { id; title }[]`; `EmployeePositionFormValues`
  gana `supervisorPositionIds: string[]` (siempre array, nunca `undefined`, para que el
  resolver de Zod y `react-hook-form` tengan tipos consistentes).
- `EmployeePositionForm`: nuevo campo "Cargo(s) supervisor(es)" con `Combobox`
  (`@restopsiq/ui`, `multiple`) sobre `useEmployeePositions()` (cargos activos del
  tenant), excluyendo el propio cargo cuando se edita. El backend es la fuente de
  validación real (self-supervision, tenant, ciclos); esto solo evita el error más obvio
  antes de enviar.
- `EmployeePositionsListScreen`: pasa `supervisors` (títulos) a `CargoTableItem` y
  `supervisorPositionIds` en los payloads de create/update.
- **Fix incidental**: el campo `baseSalaryRange` (`Controller` + `ThousandsInput`)
  llamaba a `field.onChange` con un `number`, pero el schema Zod exige `string` — el
  submit fallaba silenciosamente en cualquier flujo que tipeara el salario. Bug
  preexistente (no introducido por OS-633), descubierto al escribir el primer test de
  este formulario; corregido con `onChange={(value) => field.onChange(String(value))}`.

## 10. Decisiones técnicas

1. `EmployeePositionSupervisor` sigue siendo la única fuente de verdad de la jerarquía.
2. No se introduce `parentPositionId` en `EmployeePosition`: el modelo ya soporta
   múltiples supervisores por cargo y así se sembró el organigrama real (OS-550); un FK
   de padre único sería una regresión de expresividad.
3. No se crea tabla ni módulo nuevo — se extiende `payroll/employee-positions`.
4. La validación de ciclos vive en el **backend** (`EmployeePositionsService`), no solo en
   el frontend; el Combobox del formulario solo reduce errores obvios (excluye el propio
   cargo de las opciones).
5. El BFS de subordinados (`resolveSubordinatePositionIds`) se **extrajo a un helper
   compartido** en vez de triplicarlo — ya vivía duplicado en `attendance` y `vacations`
   (OS-550); ahora los tres repositorios (payroll, attendance, vacations) llaman a la
   misma función.
6. No se implementó un árbol/organigrama visual — la tabla + selector multiselect
   cumplen el criterio de aceptación de este ticket ("hacer visible y editable", no
   "visualizar el organigrama completo").

## 11. Dependencias

- Depende de datos existentes de OS-550 (`EmployeePositionSupervisor`, seed del
  organigrama) — no depende de ningún PR no mergeado.
- Reutiliza `Combobox` (`@restopsiq/ui`, ya existente con soporte `multiple`) — no se creó
  ningún componente de selección múltiple nuevo.

## 12. Limitaciones

- El chequeo de ciclos se hace **por operación** (al guardar un cargo), no hay un job de
  integridad que audite periódicamente si existen ciclos en datos ya persistidos (no
  debería haberlos, dado que la única vía de escritura ahora pasa por la validación, pero
  el seed de OS-550 escribe directo a Prisma sin pasar por el service).
- La relación es de **cargo a cargo**, no de empleado a empleado — sigue la decisión de
  producto original de OS-550 (comentario en `schema.prisma`).
- No hay UI para ver el organigrama completo de un vistazo (árbol/diagrama) — está fuera
  de alcance por instrucción explícita del ticket.
- **Concurrencia**: cada operación de creación/actualización es atómica en sí misma
  (`$transaction`), pero no se implementó control de concurrencia optimista, bloqueo
  explícito ni nivel de aislamiento `SERIALIZABLE` entre dos actualizaciones simultáneas
  sobre la misma jerarquía (p. ej. dos administradores editando supervisores del mismo
  cargo, o de cargos relacionados, al mismo tiempo). Se acepta como limitación dado el bajo
  volumen esperado de esta operación administrativa; una transacción por sí sola no impide
  inconsistencias lógicas entre transacciones concurrentes, solo garantiza atomicidad y
  aislamiento dentro de cada una.

## 13. Pendientes

## 14. Relación con OS-550

OS-550 creó el modelo y lo consumió exclusivamente desde `attendance` (filtro de
colaboradores por cargos subordinados) y `vacations` (aprobación por jerarquía). OS-633
no modifica esa semántica ni el contrato de `findSubordinatePositionIds` — solo extrae su
implementación a un helper compartido y la reutiliza para el chequeo de ciclos al editar
cargos. Los tests existentes de `attendance-collaborators` y `vacations` se corrieron sin
modificar sus expectativas y siguen pasando, confirmando que OS-550 no se rompió.
