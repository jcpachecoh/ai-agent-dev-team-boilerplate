## 3. Arquitectura — decisión de diseño

### 3.1 Auditoría obligatoria de escritura (paso previo, sin código)

Se identificaron **3 flujos** que escriben `salaryAmount`, `salaryType`,
`cesantiasFundName` o `pensionFundName` sobre `EmployeeDetails`, todos dentro de un
`prisma.$transaction`:

| Flujo                                                                        | Archivo                                            | Entrypoints                                                                                                                    |
| ---------------------------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Alta de empleado (formulario completo)                                       | `PayrollRepository.create()`                       | REST `POST /payroll` (`PayrollController`), GraphQL `createEmployee` (`EmployeesResolver`) — ambos vía `PayrollService.create` |
| Edición de empleado                                                          | `PayrollRepository.update()`                       | REST `PATCH /payroll/:userId`, GraphQL `updateEmployee` — ambos vía `PayrollService.update`                                    |
| Onboarding rápido de admin (placeholder `"Por definir"` / `salaryAmount: 0`) | `AdminUsersRepository.createWithEmployeeDetails()` | `AdminUsersService.create`                                                                                                     |

`AdminUsersRepository.update()` y `completeEmployeeUserProvisioning()` **no** tocan estos
4 campos (solo `email`/`roleId`/`isActive`/`locationId`/`name`) — confirmado por grep, no
requieren sync. `medical-leaves`, `payroll/mapper`, `reports/*` solo **leen** estos campos
(cálculo de incapacidades, DTOs de reporte) — no son sitios de escritura.

### 3.2 Un modelo por concepto, no un EAV genérico

Se evaluaron tres opciones:

- **3 modelos separados** (`EmployeeSalaryHistory`, `EmployeeCesantiasFundHistory`,
  `EmployeePensionFundHistory`), replicando exactamente `EmployeePositionHistory`.
- **Un modelo genérico** tipo EAV (`attribute` + `value` como columnas nullable según el
  tipo) cubriendo salario y ambos fondos en una sola tabla.
- **2 modelos** (elegido): `EmployeeSalaryHistory` (monto + tipo) y `EmployeeFundHistory`
  (con `fundType: EmployeeCatalogType`, reutilizando el enum ya existente del catálogo en
  vez de crear uno paralelo).

Se descartó el EAV genérico porque **ningún modelo en todo el schema** (2300+ líneas)
usa ese patrón — introducirlo solo para este caso habría sido una excepción arquitectónica
no justificada. Se descartaron los 3 modelos separados porque `CESANTIAS_FUND` y
`PENSION_FUND` son estructuralmente idénticos (string + vigencia) — separarlos habría
duplicado columnas, repository, service y tests sin ganar nada. `EmployeeFundHistory` con
`fundType` como discriminador reutiliza `EmployeeCatalogType` (ya usado por
`EmployeeCatalogOption`) y queda abierto a futuras vigencias de `EPS`/`ARL`/`CAJA_COMPENSACION`
si algún día se necesitan, sin nueva migración de enum.

### 3.3 Vigencias sin partial unique index (mismo patrón que `EmployeePositionHistory`)

`effectiveFrom`/`effectiveTo` (nullable = registro abierto), sin constraint de unicidad a
nivel de base de datos para "un solo registro abierto" — se investigó si existía
precedente de partial unique index (`WHERE effectiveTo IS NULL`) en el repo y no lo hay;
`EmployeePositionHistory` (el único historial de vigencias existente) tampoco lo tiene y
confía en que el service cierre antes de crear. Se replicó esa misma garantía a nivel de
aplicación, pero **reforzada**: a diferencia de `assignPositionToEmployee` (que cierra y
crea en dos llamadas _secuenciales, fuera de transacción_), aquí el cierre + creación
ocurre **dentro de la misma transacción Prisma** que el `employeeDetails.update`/`create`
que lo origina (ver §3.4) — requisito explícito de este ticket dado que se trata de datos
con implicación legal (cesantías), más estricto que el precedente de cargos.

**Riesgo residual documentado, no resuelto aquí:** sin partial unique index, una
condición de carrera con dos escrituras concurrentes sobre el mismo empleado podría dejar
dos registros abiertos. Es el mismo riesgo que ya existe en `EmployeePositionHistory`;
no se introduce uno nuevo, pero tampoco se cierra. Queda para quien implemente el cálculo
de cesantías evaluar si conviene un partial unique index en ese momento.

**Corrección aplicada en la revisión crítica posterior:** la primera versión de este
commit no restringía nada a nivel de base de datos más allá de lo que ya validaba
`EmployeeHistoryRepository` en código. Una revisión posterior encontró precedente real en
el repo para cerrar dos huecos con `CHECK` constraints (`turno_assignments_type_turno_check`
y `employee_shift_assignments_effective_range_check`, migración
`20260706160000_shift_uni_employee_assignment` — más reciente que
`EmployeePositionHistory` y ya usada en el repo, así que no es una convención nueva). Se
agregaron 3 constraints, cada una verificada manualmente contra Postgres real (INSERT que
debía fallar, falló con el mensaje esperado):

- `employee_salary_history_effective_range_check` / `employee_fund_history_effective_range_check`
  — `CHECK ("effectiveTo" IS NULL OR "effectiveTo" >= "effectiveFrom")`. Cierra el caso en
  que un `effectiveFrom` fuera de orden (p.ej. reloj de servidor desincronizado, o una
  futura corrección retroactiva mal implementada) dejaría `effectiveTo < effectiveFrom` en
  el registro que se cierra — antes esto se habría escrito sin error.
- `employee_fund_history_fund_type_check` — `CHECK ("fundType" IN ('CESANTIAS_FUND', 'PENSION_FUND'))`.
  El tipo TypeScript `EmployeeFundHistoryType` solo restringe en compilación, a través de
  `EmployeeHistoryRepository`; no protegía contra un `INSERT`/`create()` de Prisma hecho
  fuera de ese repository (por ejemplo un script futuro). Ahora la base de datos lo
  rechaza aunque el caller no pase por el repository.
- `employee_fund_history_fund_name_not_blank_check` — `CHECK (length(trim("fundName")) > 0)`.
  `NOT NULL` no protege contra `''`. Hoy la única vía pública de escritura (los DTOs
  `CreateEmployeeDto`/`CreateEmployeeInput`/sus `PartialType` de update, todos con
  `@IsNotEmpty()`) ya rechaza vacíos antes de llegar a este código — pero
  `EmployeeHistoryRepository.syncFundHistoryTx` en sí mismo no revalida nada, así que un
  caller interno futuro que no pase por esos DTOs (otro seed, un script de soporte)
  podría haber escrito `''` sin que nada lo impidiera. Ahora sí.

Las tres viven en `apps/api/prisma/migrations/20260710073204_os588_compensation_history_constraints/`
y `20260710073735_os588_fund_name_not_blank_check/`, aplicadas sobre los datos ya
backfileados sin conflicto (ninguna fila existente las viola).

### 3.4 Sincronización transaccional (`*Tx` methods)

Se encontró un único precedente en el repo para un repository method que recibe un
`Prisma.TransactionClient` externo en vez de usar `this.prisma`:
`CommitteeRepository.incrementOrdersCountTx(tx, ...)`. Se replicó ese patrón:
`EmployeeHistoryRepository.syncSalaryHistoryTx(tx, data)` /
`.syncFundHistoryTx(tx, data)` — ambos reciben el `tx` de la transacción que ya abre
`PayrollRepository.create/update` y `AdminUsersRepository.createWithEmployeeDetails`, y
ambos son **no-op si el valor no cambió** (comparan contra el registro abierto actual
antes de cerrar/crear). Esto permite invocarlos incondicionalmente en `create` (no hay
valor previo que comparar) y condicionalmente en `update` (solo si el campo vino en el
patch), sin arriesgar escribir un registro vacío o duplicado.

`PayrollRepository` y `AdminUsersRepository` ahora inyectan `EmployeeHistoryRepository`
como dependencia (repository → repository). No hay precedente exacto de esto en el repo,
pero es la única forma de garantizar la transacción única pedida por el ticket sin mover
la orquestación del `$transaction` fuera del repository (que habría sido un refactor
mucho más grande de `PayrollService`/`PayrollController`/`EmployeesResolver`).

### 3.4.1 Prueba real de rollback transaccional (no solo teórica)

El requisito "un fallo en el historial revierte también la actualización de
`EmployeeDetails`" no se apoya únicamente en que Prisma garantiza esto por diseño de
`$transaction` — se verificó con un script ejecutado contra Postgres real (no mocks):

1. Se leyó un empleado real y su vigencia salarial abierta.
2. Dentro de un `$transaction`, se actualizó `EmployeeDetails.salaryAmount` y luego se
   llamó `syncSalaryHistoryTx` con un `effectiveFrom` deliberadamente anterior en 5 años al
   de la vigencia abierta — forzando la violación del nuevo CHECK de rango.
3. La transacción lanzó el error esperado.
4. Se releyó el empleado y su historial: **`salaryAmount` y la vigencia abierta quedaron
   exactamente igual que antes** — el `update` de `EmployeeDetails` también se revirtió,
   pese a haber ocurrido "antes" en el mismo callback.

Además, se agregaron tests unitarios (`employee-history.repository.spec.ts`,
`payroll.repository.spec.ts`) que confirman que ni `EmployeeHistoryRepository` ni
`PayrollRepository.create()` atrapan/silencian un error del paso de sincronización — se
propaga tal cual hacia el caller, que es la otra mitad de la garantía (si el código
tuviera un `try/catch` que tragara el error, la transacción igual habría hecho rollback en
la base de datos, pero el caller HTTP/GraphQL habría recibido una respuesta 200 con datos
inconsistentes en la respuesta serializada — no ocurre, se confirmó que no hay ningún
`try/catch` dentro de `PayrollRepository`/`AdminUsersRepository` que pudiera enmascarar
esto).

### 3.4.2 Limitación explícita: no hay forma de indicar una fecha efectiva retroactiva

Ninguno de los tres flujos de escritura permite al caller especificar `effectiveFrom`.
Siempre es:

- **Creación de empleado:** `contractStart` del propio payload (nunca "hoy").
- **Edición de empleado:** `new Date()` — el momento exacto en que corre la transacción.
- **Backfill / seeds:** `COALESCE(contractStart, hireDate, createdAt)`.

Esto significa que **hoy no existe manera de corregir retroactivamente un dato histórico
con su fecha real.** Si el 10 de julio se corrige un error de digitación de un salario que
debió haber cambiado el 1 de marzo, el sistema abre la nueva vigencia el 10 de julio, no
el 1 de marzo — dejando una vigencia incorrecta "vigente" entre marzo y julio en los
registros históricos. Para la liquidación anual de cesantías esto es un problema real: una
corrección tardía de un dato de meses atrás no recalculará correctamente los días
causados a la tasa correcta.

**No se resuelve en esta fase** porque implica decisiones de producto (¿quién puede
corregir retroactivamente? ¿se re-valida que no rompa la vigencia siguiente? ¿se
audita distinto una corrección retroactiva de un cambio real?) que exceden "solo
infraestructura". Queda como requisito explícito para la fase de cálculo: el mínimo
necesario sería agregar un parámetro opcional `effectiveFrom`/`asOfDate` al flujo de
edición, restringido a un rol/permiso distinto del de edición normal, y validado contra
las vigencias adyacentes (los nuevos CHECK de rango de esta fase ya rechazarían un valor
que invierta el orden, pero no validan solapamiento contra una vigencia _posterior_ ya
cerrada intermedia — ese caso necesitaría lógica de aplicación adicional).

### 3.4.3 `resolveInitialEffectiveDate` — la cadena de fallback es en su mayoría teórica hoy

`contractStart` y `hireDate` son columnas `NOT NULL` en `EmployeeDetails` (nunca
opcionales). En la práctica, tanto en el flujo de creación en vivo como en el backfill SQL,
el primer término (`contractStart`) siempre gana — los fallbacks a `hireDate`/`createdAt`
son defensivos (tipados como opcionales para poder reutilizar la función también desde
los seeds, donde en teoría un caller distinto podría no tenerlos), pero no se ejercitan
con los datos reales de hoy. Esto no es un bug, pero se documenta para que quede claro que
no hay evidencia real de que la prioridad 2 o 3 alguna vez se haya activado.

### 3.5 `EmployeeDetails.salaryAmount` se mantiene intacto

Por requisito explícito: `salaryAmount`/`salaryType`/`cesantiasFundName`/`pensionFundName`
en `EmployeeDetails` siguen siendo el snapshot vigente, sin cambios de tipo ni de
semántica. `PayrollCalculationService` (NOM-04) sigue leyéndolos exactamente igual — cero
cambios en ese archivo.

## 4. Modelo de datos

```prisma
model EmployeeSalaryHistory {
  id                String     @id @default(cuid())
  tenantId          String
  employeeDetailsId String
  salaryType        SalaryType
  salaryAmount      Decimal    @db.Decimal(12, 2)
  effectiveFrom     DateTime
  effectiveTo       DateTime?
  changedBy         String?
  createdAt         DateTime   @default(now())

  employee EmployeeDetails @relation(fields: [employeeDetailsId], references: [id], onDelete: Cascade)

  @@index([tenantId, employeeDetailsId])
  @@index([employeeDetailsId, effectiveFrom])
  @@map("employee_salary_history")
}

model EmployeeFundHistory {
  id                String              @id @default(cuid())
  tenantId          String
  employeeDetailsId String
  fundType          EmployeeCatalogType // solo CESANTIAS_FUND | PENSION_FUND
  fundName          String
  effectiveFrom     DateTime
  effectiveTo       DateTime?
  changedBy         String?
  createdAt         DateTime            @default(now())

  employee EmployeeDetails @relation(fields: [employeeDetailsId], references: [id], onDelete: Cascade)

  @@index([tenantId, employeeDetailsId, fundType])
  @@index([employeeDetailsId, fundType, effectiveFrom])
  @@map("employee_fund_history")
}
```

`schema.prisma` no puede expresar los `CHECK` agregados en la revisión crítica (§3.4)
— viven solo en las migraciones SQL, no en el modelo Prisma (mismo patrón que
`turno_assignments`/`employee_shift_assignments`, que tampoco los declaran en el schema):

- `employee_salary_history_effective_range_check`
- `employee_fund_history_effective_range_check`
- `employee_fund_history_fund_type_check`
- `employee_fund_history_fund_name_not_blank_check`

Migraciones (`apps/api/prisma/migrations/`), en orden:

1. `20260710062818_os588_employee_compensation_history` — `CREATE TABLE` de ambos modelos.
2. `20260710063101_os588_backfill_compensation_history` — backfill SQL (ver §5).
3. `20260710073204_os588_compensation_history_constraints` — CHECK de rango de vigencia
   (ambas tablas) + CHECK de `fundType` restringido.
4. `20260710073735_os588_fund_name_not_blank_check` — CHECK de `fundName` no vacío.

Las migraciones 3 y 4 se aplicaron **después** del backfill (migración 2) contra los
datos ya backfileados, sin conflicto — ninguna de las 318 filas existentes (106 + 212)
las viola.

## 5. Backfill

Un solo `INSERT ... SELECT` por tabla, incluyendo **todos** los `employee_details`
existentes (activos, inactivos y con soft-delete). Decisión deliberada: un empleado que se
retiró durante el año fiscal igual causó cesantías hasta su fecha de retiro, así que su
historial debe poder reconstruirse aunque el registro tenga `deletedAt`.

`effectiveFrom` usa `COALESCE(contractStart, hireDate, createdAt)` — la misma regla que
aplica el código de aplicación para empleados nuevos
(`resolveInitialEffectiveDate`, `apps/api/src/payroll/utils/employee-history-effective-date.util.ts`),
para no duplicar el criterio entre el backfill SQL y el flujo de creación en código.
IDs generados con `gen_random_uuid()` (nativo en Postgres 16, sin necesitar `pgcrypto`).

Verificado contra la base de datos de desarrollo real: **106 empleados → 106 filas en
`employee_salary_history` + 212 en `employee_fund_history`** (106 cesantías + 106
pensión), sin colisiones. Se confirmó también contra la data real que ningún
`employee_details` existente tiene `salaryAmount = 0` ni `cesantiasFundName`/
`pensionFundName` vacíos hoy — el caso "valor vacío que no representa un cambio válido"
es teórico en este dataset, no observado.

**Base limpia vs base existente:** en una base limpia (`prisma migrate deploy` sobre una
DB vacía, sin `employee_details` todavía) el `INSERT ... SELECT` de esta migración no
encuentra filas y no inserta nada — no falla, es un no-op seguro. Los empleados que se
creen después vía seeds quedan cubiertos por el fix de §7, no por este backfill.

**Reversibilidad:** no hay `down.sql` — ninguna migración de este repo lo tiene (Prisma
Migrate no genera reversa automática; es el patrón estándar del proyecto). Un rollback
selectivo de "solo el backfill" no está soportado. Si se necesitara revertir toda esta
fase de infraestructura, el camino es una migración nueva que haga `DROP TABLE
employee_salary_history, employee_fund_history` — como ambas tablas se crean en esta
misma fase (no existían antes), esa reversión es completa y no deja estado huérfano.

**Idempotencia de la migración en sí** (no confundir con la idempotencia de los seeds,
§7): cada `INSERT` tiene su propio `WHERE NOT EXISTS`, así que ejecutar el archivo SQL
dos veces manualmente (fuera del flujo normal de Prisma, que nunca re-aplica una
migración ya registrada) no duplicaría filas.

## 7. Seeds

**Corrección encontrada durante la validación de la fase 2 (§23.3 Parte 2) — se documenta
aquí porque es un hallazgo de esta misma auditoría de la fase 1, no de la fase 2:** al
probar la migración sobre una base de datos limpia con `prisma migrate deploy` + seed
completo, aparecieron **106 `employee_details` pero solo 102 `employee_salary_history`** —
4 empleados sin historial. La búsqueda original de la fase 1 (`grep` sobre
`apps/api/prisma/seeds/*.ts`) no incluyó `apps/api/prisma/seed.ts` (el orquestador
principal, un nivel arriba de la carpeta `seeds/`), que también crea `EmployeeDetails`
directamente en 4 `upsert()` (owner, operator, supervisor y manager de demo —
`seedEmployeeDetails`/`seedSupervisorManagerDemoUsers`). Corregido ahora: los 4 upserts
capturan la fila devuelta y llaman `syncEmployeeCompensationHistory` (el mismo helper ya
existente, sin lógica nueva). Verificado sobre una base limpia: **106/106 tras la
corrección**, y una segunda corrida del seed completo no duplica nada (mismos conteos:
106/106/212). La base de datos de desarrollo compartida (`restopsiq_dev`) no tenía este
gap porque el backfill SQL de la migración corrió sobre datos que ya incluían estos 4
empleados — el gap solo se manifiesta en una base nueva/limpia, que es exactamente donde
se detectó.

Dos seeds más (dentro de `apps/api/prisma/seeds/`) crean `EmployeeDetails` directamente
vía Prisma (fuera de `PayrollRepository`): `plant-supervisor.seed.ts` y
`attendance-collaborators-bulk.seed.ts`. Sin cambios, un `prisma migrate reset` en un
entorno nuevo habría dejado esos empleados sin historial (el backfill SQL solo cubre filas
que ya existían _al momento de correr la migración_, no las creadas después por seeds).

Se agregó `prisma/seeds/employee-compensation-history.seed-util.ts`
(`syncEmployeeCompensationHistory`) — reutiliza `EmployeeHistoryRepository` y
`resolveInitialEffectiveDate`, la misma lógica que usa el código de aplicación, invocada
después de cada `employeeDetails.upsert()` en ambos seeds. Verificado en runtime contra la
base de datos de desarrollo:

- Primera corrida: sin romper nada existente, con recomputo de `salaryAmount` distinto al
  backfill original para ~75 empleados (porque el seed deriva el salario de
  `position.baseSalaryRange`, que no coincidía exactamente con el valor backfileado) →
  **se abrió correctamente una nueva vigencia y se cerró la anterior**, confirmando que la
  detección de cambios funciona con datos reales, no solo en mocks.
- Segunda corrida (reseed): **cero filas nuevas** — confirma idempotencia (`salaryCount`/
  `fundCount` idénticos antes y después de repetir `seedBulkAttendanceCollaborators`).

**Fragilidad conocida, aceptada:** `syncEmployeeCompensationHistory` instancia
`EmployeeHistoryRepository` manualmente (`new EmployeeHistoryRepository({} as never)`) en
vez de resolverlo por DI de Nest, porque los seeds corren como scripts planos vía `tsx`,
fuera del contenedor de Nest. Esto funciona porque el seed solo llama a
`syncSalaryHistoryTx`/`syncFundHistoryTx`, que reciben su cliente Prisma como parámetro
(`tx`) y nunca tocan `this.prisma`. Si en el futuro se agrega a `EmployeeHistoryRepository`
un método que sí use `this.prisma` y alguien lo invoca desde un seed sin darse cuenta de
esta restricción, fallará en tiempo de ejecución con un error confuso (`Cannot read
properties of undefined`). Se documenta aquí explícitamente para que quien toque ese
archivo lo tenga presente — no se le puso una guarda en código porque hubiera sido
sobre-ingeniería para un caso que hoy no ocurre.

# Parte 2 — Motor de cálculo, persistencia y consulta (esta fase)

## 12. Auditoría obligatoria previa (paso 1 de esta fase, antes de tocar código)

Se revisó el código real (no se asumió nada) antes de diseñar. Hallazgos:

### 12.1 `PayrollCalculationService` (NOM-04) — no reutilizable para cesantías

Es una función **pura** (`apps/api/src/payroll/service/payroll-calculation.service.ts`),
sin acceso a base de datos y **sin persistencia** — `ReportsService.getPayrollReport` la
invoca al vuelo para generar un reporte, pero el resultado (`EmployeePayrollPeriod`) nunca
se guarda en ninguna tabla. Confirmado con `grep` en `reports.service.ts`: no hay
`prisma.*.create/upsert` del resultado del cálculo, solo se serializa a PDF/Excel/JSON de
respuesta. **No existe ningún "resultado o acumulado de nómina persistido"** en el schema
— se buscó explícitamente y no hay tabla `PayrollRun`/`PayrollResult`/similar.

Además, opera en `number`/`Math.round`, con `employee.salaryAmount` como **el valor
actual único** de `EmployeeDetails` (no historizado) — exactamente el problema que la fase
1 resolvió para cesantías, pero NOM-04 nunca lo necesitó porque solo liquida el mes
corriente.

**Conclusión:** no se creó un motor paralelo. Se construyó un motor **nuevo pero
complementario** (`CesantiasCalculationService`), consumiendo una fuente de datos que NOM-04
no tiene (`EmployeeSalaryHistory`) para un problema que NOM-04 no resuelve (acumulación
anual). No hay duplicación porque no hay superposición de responsabilidad — NOM-04 sigue
intacto, sin un solo archivo modificado en esta fase.

### 12.2 Reutilizado tal cual de NOM-04 (sin copiar código, mismos criterios)

- **Elegibilidad de auxilio de transporte**: `hasTransportSubsidy && salaryType !== INTEGRAL && salaryAmount <= 2×SMLV` — mismo criterio exacto que `PayrollCalculationService.calculateEmployeePeriod` (línea `eligibleForSubsidy`).
- **Resolución de parámetros legales "planos por periodo"**: `ReportsService.getPayrollReport` resuelve `SMLV`/`AUXILIO_TRANSPORTE` **una sola vez, a la fecha final del periodo** (comentario explícito en el código: _"resolved once, as of the period's last day"_) — se replicó el mismo criterio para `INTERES_CESANTIAS`/`DIVISOR_CESANTIAS`/`AUXILIO_TRANSPORTE`/`SMLV` en `CesantiasService`, con la misma justificación (sus vigencias empiezan el 1 de enero, y el periodo de una liquidación anual nunca cruza un 1 de enero).
- **`LaborLegalParametersService.preload(...)` + `LegalParameterSnapshot`**: usado exactamente como en `ReportsService` — una sola resolución en batch antes de iterar empleados, evita N+1.

### 12.3 `EmployeeSalaryHistory`/`EmployeeFundHistory`/`EmployeeDetails`/`LaborLegalParameter` (fase 1)

Ya documentados en la Parte 1. Se reutilizan sin cambios de esquema salvo lo indicado en
§12.4. La fuente de verdad para cada dato requerido se resume en §13.

### 12.4 Extensión no-destructiva de `EmployeeHistoryRepository`

Se agregaron `findSalaryHistoryByEmployees`/`findFundHistoryByEmployees` (plural, batch)
al repository existente de la fase 1 — **no se creó un repository paralelo**. Los métodos
singulares (`findSalaryHistoryByEmployee`) que expone `EmployeeHistoryService` no sirven
para un cálculo de tenant completo (N llamadas = N+1); los nuevos métodos batch consultan
una sola vez con `employeeDetailsId: { in: [...] }` y agrupan en memoria. Por eso
`CesantiasService` inyecta `EmployeeHistoryRepository` directamente en vez de
`EmployeeHistoryService` — el Service de la fase 1 deliberadamente no expone escritura
(ver su comentario de diseño) y tampoco expone batch-read, que es exactamente lo que esta
fase necesita agregar; agregarlo al Repository (no al Service) mantiene esa capa de
lectura acotada al propósito original ("un empleado a la vez, para pantallas de detalle").

### 12.6 Patrones existentes de liquidaciones y de estados

`EmployeePaymentHistory` (`apps/api/prisma/schema.prisma`, módulo OS-559) es el precedente

## 14. Limitaciones documentadas (datos que el repo no puede sustentar hoy)

Siguiendo la instrucción explícita de no inventar datos ni ampliar el alcance sin
autorización, estos casos **no se implementaron** y quedan documentados en vez de
adivinados:

### 14.1 Auxilio de transporte — elegibilidad no historizada

`EmployeeDetails.hasTransportSubsidy` es un flag **actual**, no un campo de
`EmployeeSalaryHistory`. Si un empleado dejó de ser elegible (p.ej. superó el umbral de 2
SMLV) o empezó a serlo a mitad del año, el cálculo aplica el flag **de hoy** a todos los
tramos retroactivamente. Aproximación documentada, no oculta.

### 14.2 Salario variable / conceptos variables (comisiones, bonificaciones)

No hay ningún modelo en el repo que historice conceptos variables por periodo. El cálculo
usa exclusivamente `EmployeeSalaryHistory.salaryAmount` (el fijo). Si un empleado tiene
salario variable real, la liquidación calculada será **incompleta** — no incorrecta por
un bug, sino incompleta por falta de fuente. Debe documentarse como gap de producto, no
resolverse con una fórmula inventada.

### 14.3 Suspensiones, licencias no remuneradas, incapacidades — no excluidas de días causados

`MedicalLeave` (incapacidades) y ausencias no se restan de `accrualDays`. Se evaluó
integrarlas y se decidió NO hacerlo en esta fase porque: (a) el tratamiento legal de qué
días de incapacidad cuentan o no para cesantías tiene reglas propias que no están
modeladas ni confirmadas en el repo (a diferencia de NOM-04, que sí excluye días de
incapacidad de la base **salarial mensual**, un cálculo distinto); (b) integrar esa regla
sin una fuente de verdad clara sería "inventar datos". El accrual actual asume el año
completo trabajado salvo por fecha de ingreso/retiro — una sobreestimación conocida y
documentada para empleados con incapacidades/licencias largas.

### 14.4 Registros de asistencia — deliberadamente NO usados como proxy de días causados

Se decidió explícitamente NO usar `AttendanceLog` para inferir días causados. La
arquitectura existente no define esa equivalencia en ningún lugar (NOM-04 usa asistencia
para el pago del MES, no para prestaciones anuales) — usar asistencia habría sido
inventar una regla nueva no pedida.

### 14.5 Tipo de contrato — `APRENDIZAJE` excluido por precaución, no por certeza legal

Ver `CESANTIAS_EXEMPT_CONTRACT_TYPES` en `cesantias.service.ts`. `PRESTACION` se excluye
con alta confianza (no es relación laboral). `APRENDIZAJE` tiene un régimen especial (Ley
789/2002, etapa lectiva vs práctica) que **no se modeló en detalle** — se excluye por
precaución (subestimar es más seguro que inventar una regla), pero requiere validación
legal antes de considerarse la respuesta correcta y definitiva.

### 14.6 Fecha efectiva retroactiva — sigue sin existir (heredado de la fase 1, no resuelto aquí)

La fase 1 ya documentó que no hay forma de insertar una vigencia salarial/de fondo con
fecha pasada. Esto se hereda directamente como limitación de la fase 2: si el historial
salarial de un empleado tiene un hueco o un dato incorrecto para años anteriores a esta
implementación (2026-07-10), la liquidación de esos años usará lo que haya en
`EmployeeSalaryHistory` en ese momento — que, para años previos al backfill de la fase 1,
es el **último valor conocido al momento del backfill**, no necesariamente el valor
históricamente correcto. Ver Parte 1 §3.4.2/§3.4.3.

### 16.1 No se creó un modelo genérico de prestaciones

Se buscó explícitamente si existía una entidad reutilizable de "liquidación"/"prestación"
antes de crear una nueva (instrucción explícita) — no existe (§12.6). El modelo es
específico a cesantías, con el mínimo de campos pedidos.

### 16.2 `year Int`, no `period String`

Se evitó deliberadamente el antipatrón visto en `DotacionDelivery.period` (`"2026-04"`,
string libre) — mismo criterio que `EmployeePaymentHistory.periodYear`. `periodStart`/
`periodEnd` (`@db.Date`) documentan el rango real considerado (importante porque puede ser
menor a un año completo: ingreso/retiro mid-año, o el cálculo corrido antes de que termine
el año en curso — ver §17.2).

### 16.3 `onDelete: Restrict`, no `Cascade`

Toda otra relación hacia `EmployeeDetails` en el schema usa `Cascade` (incluidas
`EmployeeSalaryHistory`/`EmployeeFundHistory` de la fase 1). Se usó `Restrict` aquí a
propósito — mismo criterio que `MedicalLeave.employee` (el único otro registro legal con
implicación financiera hacia terceros, que también usa `Restrict`). Una liquidación de
cesantías no debería poder desaparecer silenciosamente si alguna vez se hard-deletea un
`EmployeeDetails` (lo cual ya está prohibido por convención del proyecto, pero `Restrict`
lo hace imposible incluso ante un error).

### 16.4 Sin soft delete — reversión vía estado, no vía `deletedAt`

Se investigó explícitamente antes de agregar `deletedAt` por reflejo (instrucción del
ticket). `EmployeePaymentHistory` (el precedente más cercano) tampoco lo tiene. La
reversión/anulación de una liquidación legal ya calculada no es "borrarla" — es un cambio
de estado auditable (`ANULADA`/`ANULADO`) que preserva el historial de qué se calculó y
cuándo. Un soft delete aquí habría permitido "esconder" una liquidación sin dejar rastro
de que existió, lo cual es peor para un registro con implicación legal/fiscal que
simplemente no tener soft delete.

### 16.5 `@@unique([employeeId, year])` — evaluado explícitamente contra versionado futuro

Instrucción explícita: no usar una restricción que bloquee una estrategia de versionado
futura sin haberlo evaluado. Se evaluó la alternativa (sin `@@unique`, agregando
`version Int` + `isCurrent Boolean` para permitir múltiples cálculos históricos por
año) y se **descartó para esta fase**: added complexity sin un caso de uso confirmado
(nadie pidió conservar cálculos intermedios, solo "recalcular"). La restricción única
actual:

- Es aditiva-reversible: quitarla en el futuro (`DROP CONSTRAINT`) no pierde datos ni
  rompe filas existentes, si luego se decide versionar.
- Es la misma forma que ya usa `EmployeePaymentHistory` (`@@unique([financialProfileId, periodYear, periodMonth])`) para el precedente más cercano.

Si el equipo decide más adelante que se necesita conservar el historial de recálculos
(auditoría de "qué se calculó antes de corregir"), la vía recomendada NO es quitar el
unique sino agregar una tabla `CesantiasLiquidationRecalculation` (append-only, log de
cambios) sin tocar la unicidad de la tabla principal — evaluado pero no implementado por
no estar en el alcance pedido.

### 16.6 Canal de fondo (`CesantiasFundChannel`) — heurística documentada, no un dato real

No existe ninguna columna de canal en `EmployeeCatalogOption`/`EmployeeFundHistory` (fase

1. — el catálogo de fondos es una lista plana de nombres (`prisma/seeds/employee-catalog.seed.ts`).
   `fundChannelSnapshot` se deriva comparando el nombre exacto contra `"Fondo Nacional del
Ahorro"` (el nombre real sembrado, no la sigla "FNA"). Riesgo documentado: si un tenant
   llegara a tener un nombre de fondo distinto para el FNA (typo, variante de nombre), la
   heurística lo clasificaría como `PRIVATE_OPERATOR` incorrectamente. No se resolvió porque
   requeriría agregar una columna de canal al catálogo — fuera del alcance de esta fase.

## 17. Cálculo salarial por vigencias y regla de fondo

Implementado en `apps/api/src/payroll/utils/cesantias-days.util.ts` (puro, sin DB) +
`apps/api/src/payroll/service/cesantias-calculation.service.ts` (fórmula, puro, sin DB).

### 17.1 Días causados — convención comercial 30/360, no días de calendario reales

`commercialDaysBetween(start, endExclusive)` implementa la convención legal colombiana
estándar (CST art. 249 / Ley 50 de 1990): cada mes cuenta 30 días sin importar los días
reales (así febrero cuente 30 "días de cesantías" aunque tenga 28). Un año completo
[2026-01-01, 2027-01-01) = exactamente 360. Documentado con ejemplos verificados en tests.

### 17.2 Ventana de cálculo — se topa en "hoy" para el año en curso

`resolveYearWindow(year)`: `periodEnd` es `min(31-dic-year, hoy)`. Para años ya cerrados,
`hoy` no aplica (siempre > 31-dic de un año pasado). Para el año en curso, esto evita
"causar" días futuros que aún no han ocurrido si alguien corre el cálculo en julio para el
año en curso — el resultado es una liquidación **parcial y recalculable**, no un error.
Documentado explícitamente: correr el cálculo antes del cierre del año es válido y
produce un resultado parcial, no una liquidación "final".

### 17.3 Tramos salariales — `resolveSalarySegments`

Recorta cada vigencia de `EmployeeSalaryHistory` a la ventana [inicio empleo ∩ año, fin
empleo ∩ año]. No hay doble conteo por construcción: las vigencias de la fase 1 ya
garantizan no-solapamiento (`syncSalaryHistoryTx`), y el recorte solo intersecta, nunca
combina. Verificado con tests explícitos que suman los días de los tramos y confirman que
el total es exactamente el esperado.

Casos manejados explícitamente (con test dedicado cada uno):

- Empleado activo todo el año → 1 tramo, 360 días.
- Ingreso durante el año → tramo recortado desde `hireDate`.
- Retiro durante el año → tramo recortado hasta `contractEnd + 1 día` (exclusivo).
- Cambio salarial (2+ tramos) → suma exacta sin solapamiento.
- Cambio de tipo salarial (ORDINARIO→INTEGRAL) → el tramo INTEGRAL se excluye del cálculo (§17.4), no se cuenta como si fuera ORDINARIO.

### 17.4 Salario INTEGRAL — excluido de la base de cesantías

CST art. 132: el salario integral ya incorpora el factor prestacional (que cubre
cesantías, entre otras prestaciones) — no se liquidan cesantías tradicionales adicionales
sobre esa porción. Implementado en `CesantiasCalculationService.calculate`: un tramo
`INTEGRAL` aporta `0` a `accrualDays`/`cesantiasAmount`, pero **sí aparece** en el desglose
de tramos (`includedInBase: false`) para que quede trazable por qué no contó.

### 17.5 Regla de fondo — vigente al cierre, snapshot único, sin dividir consignación

`resolveFundAtDate(fundHistory, CESANTIAS_FUND, asOfDate)` — `asOfDate` es el último
instante de la ventana de cálculo (cierre de año o fecha de retiro). Ejemplo del ticket
verificado con test explícito: Protección hasta agosto, FNA desde septiembre → el fondo
snapshot es FNA. **No se divide la consignación** entre fondos anteriores — se toma
literalmente el fondo vigente en `asOfDate`, un único resultado, nunca una lista. Una
liquidación ya `CONSIGNADA`/`interestStatus PAGADO` no se recalcula aunque el empleado
cambie de fondo después (§18.3) — el snapshot ya guardado no se toca.

Si el empleado nunca tuvo una vigencia de `CESANTIAS_FUND` cubriendo `asOfDate`
(`empleado sin fondo`), se omite esa liquidación (`SIN_FONDO_CESANTIAS_VIGENTE`) — no se
inventa un fondo ni se deja el campo vacío.

## 18. Fórmulas y redondeo

`CesantiasCalculationService.calculate` (Decimal, no `number` — ver justificación en el
docblock del archivo: NOM-04 usa `number` para un solo mes; esta fase suma hasta 12 tramos
por año, más superficie para arrastre de error de punto flotante, y ya consume `Decimal`
de `EmployeeSalaryHistory`/`LaborLegalParameter`).

Por tramo (sin redondear, precisión completa de `Decimal`):

```
elegibleAuxilio = !isIntegral && hasTransportSubsidy && salario ≤ 2×SMLV
baseTramo       = isIntegral ? 0 : salario + (elegibleAuxilio ? AUXILIO_TRANSPORTE : 0)
cesantiasTramo  = isIntegral ? 0 : baseTramo × díasComercialesTramo / DIVISOR_CESANTIAS
```

Total (redondeo ÚNICO, al final, `ROUND_HALF_UP`, 2 decimales — mismo criterio que
`resolveDailySalary` en `medical-leave-payment.utils.ts`):

```
cesantiasAmount = round2( Σ cesantiasTramo )
interestAmount  = round2( cesantiasAmount × INTERES_CESANTIAS × accrualDays / DIVISOR_CESANTIAS )
calculationBase = round2( Σ(baseTramo × díasTramo) / accrualDays )   [informativo, ver §16 nota del modelo]
```

`interestAmount` con `accrualDays/DIVISOR_CESANTIAS` unifica año completo (=1, interés
pleno) y año parcial (proporcional) en una sola fórmula, sin ramas — matemáticamente
equivalente a "cesantías × tasa" cuando `accrualDays = 360`.

**No se redondea por tramo** — solo el total. Redondear cada tramo y sumar habría
arrastrado error de redondeo acumulado en años con muchos cambios salariales; se evitó a
propósito y se documenta explícitamente aquí porque no es obvio a simple vista del código.

Verificado con un test que produce una fracción no exacta (100/360 de un salario) y
confirma el redondeo `ROUND_HALF_UP` a 2 decimales.

## 19. Servicio — `CesantiasService.calculateForYear(tenantId, year, userId?)`

### 19.1 Multi-tenant

Toda lectura (`payrollRepository.findAll`, `findSalaryHistoryByEmployees`,
`findFundHistoryByEmployees`, `findMapByTenantAndYear`, `preload`) recibe `tenantId`
explícito. Verificado con un test dedicado que confirma los argumentos exactos de cada
llamada.

### 19.2 Eficiencia — sin N+1

Consultas por corrida, independiente de la cantidad de empleados:

1. `payrollRepository.findAll` — 1 query (todos los empleados del tenant, incluidos inactivos).
2. `findSalaryHistoryByEmployees` — 1 query (`employeeDetailsId IN [...]`).
3. `findFundHistoryByEmployees` — 1 query.
4. `findMapByTenantAndYear` — 1 query (liquidaciones existentes, para decidir qué saltar).
5. `legalParametersService.preload` — 1-2 queries (tenant override + global).

El cálculo puro (segmentos, fórmula) ocurre en memoria, sin DB. Solo la escritura final
(`saveCalculations`) toca la base de datos otra vez, dentro de una transacción — ver 19.3.
Verificado con la corrida real end-to-end contra 50 empleados de datos de desarrollo (ver
§22): mismo número de queries de lectura sin importar cuántos empleados calificaron.

### 19.3 Transaccional — una sola transacción para todo el lote, no una por empleado

Instrucción explícita: ni una transacción por empleado, ni una transacción que incluya
lecturas/cálculos innecesarios. Se separó en dos fases:

1. **Fuera de transacción**: todas las lecturas + todo el cálculo puro (no toca DB).
2. **Dentro de una única transacción** (`CesantiasRepository.saveCalculations`): solo los
   `upsert` de las liquidaciones que sí deben escribirse.

Verificado con:

- Test unitario (mock) que confirma que un fallo a mitad del lote se propaga sin ser
  silenciado.
- **Prueba real contra Postgres** (script ejecutado y descartado en esta sesión, no
  forma parte del repo): 3 upserts en un lote, el tercero con un `employeeId` inexistente
  (viola FK) → los 3, incluidos los 2 válidos anteriores, se revirtieron. Confirmado con
  conteo de filas antes/después (`0` → `0`) y `threw: true`.

### 19.4 Idempotente y seguro ante recálculo

`@@unique([employeeId, year])` + `upsert` → calcular dos veces no duplica (verificado con
test que corre `calculateForYear` dos veces y confirma que ambas escriben para el mismo
`employeeId`, y con la corrida real end-to-end: segunda corrida → `created: 0, updated: 32`).

Antes de calcular, se lee `findMapByTenantAndYear` (una sola query) y se decide **por
empleado**:

| Estado existente | Acción |
| --- | --— |
| No existe liquidación | Crear |
| `CALCULADA` + `CALCULADO` (nada cerrado) | Recalcular (`update` in place) |
| `ANULADA` y/o `ANULADO` | Recalcular (permite volver a calcular tras anular) |
| `CONSIGNADA` (cesantías cerradas) | **Saltar por completo** — no se toca ni cesantías ni intereses |
| `PAGADO` (intereses cerrados) | **Saltar por completo** — mismo criterio, todo o nada por registro |

Se decidió "todo o nada" (si CUALQUIERA de los dos está cerrado, se salta el registro
entero) en vez de actualizar solo el campo abierto, porque `calculationBase`/`accrualDays`
son compartidos entre ambos cálculos — actualizar cesantías sin tocar intereses (o
viceversa) dejaría el registro internamente inconsistente (unos campos reflejando el
recálculo, otros el cálculo viejo). Documentado aquí porque no es la única opción posible
y alguien podría razonablemente esperar una actualización parcial.

### 19.5 Reproducible

Dado el mismo estado de `EmployeeSalaryHistory`/`EmployeeFundHistory`/
`LaborLegalParameter`, el mismo `tenantId`+`year` siempre produce el mismo resultado — no
hay aleatoriedad ni dependencia de orden de iteración en la fórmula (el orden de
`Array.map`/`for` no afecta una suma).

### 19.6 Auditable

`calculatedBy` (opcional, el `userId` del actor que disparó el cálculo) + `calculatedAt`

- `createdAt`/`updatedAt` en cada registro. No se integró con `AuditService` (el patrón de
  audit log genérico usado en `PayrollService`/`LaborLegalParametersService`) — evaluado y
  descartado para esta fase porque `calculatedBy`/`calculatedAt` ya cubren "quién y cuándo"
  para este caso de uso específico (un batch, no un CRUD de un solo registro); agregar
  `AuditService.log` por cada una de N liquidaciones en el mismo lote habría sido ruido
  proporcional a N sin aportar información nueva. Documentado como decisión, no como
  omisión accidental.

#### 26.3.1 Por qué "Salario Mensual($)" usa `calculationBase` y no otro campo

Revisado explícitamente antes del commit contra la alternativa obvia,
`EmployeeDetails.salaryAmount` (el salario **actual/en vivo** del empleado):

- `calculationBase` es el **único campo salarial persistido directamente en la
  liquidación** (`CesantiasCalculationService.calculate`: `weightedBaseSum /
accrualDays`, ver §18 Parte 2). Es la base ponderada por días que **realmente produjo**
  el `cesantiasAmount` de esa misma fila — auditable internamente: quien reciba el
  archivo puede verificar `cesantiasAmount ≈ calculationBase × accrualDays / divisor`
  usando solo columnas del propio archivo.
- `EmployeeDetails.salaryAmount` es un campo **mutable, sin snapshot**, leído al momento
  de exportar — no al momento en que se calculó la liquidación. Si el empleado tuvo un
  aumento/cambio salarial entre el cierre de la liquidación (fase 2) y el momento de la
  exportación (fase 3, pudiendo ser meses después), `salaryAmount` ya no reflejaría el
  salario que efectivamente sustentó el valor consignado en esa fila — rompería la
  consistencia interna del archivo y la trazabilidad regulatoria (un archivo de
  consignación debe reflejar lo que se calculó, no el estado actual del empleado).
  `salaryAmount` tampoco existe en `CesantiasLiquidation` — usarlo violaría además "no
  recalcular nada, reutilizar solo lo ya calculado" (requisito explícito de esta fase),
  porque implicaría ir a buscar un dato fuera de la liquidación persistida.
- **Salvedad documentada, no resuelta**: `calculationBase` puede incluir el auxilio de
  transporte cuando aplicó (`segmentBase = salaryAmount + auxilioTransporte` si
  corresponde, ver `CesantiasCalculationService.calculate`). No existe en el modelo
  ningún campo separado con "solo el salario base sin auxilio" — la liquidación nunca
  persistió esa desagregación porque no se pidió en fase 2. Si "Salario Mensual($)" en el
  formato real del FNA debe excluir el auxilio de transporte, este valor no lo hace
  correctamente hoy. No se resolvió inventando un nuevo cálculo (violaría "no
  recalcular") — queda documentado como riesgo en §29.

### 26.5 Empleados sin `EmployeePersonalData` — exportación parcial, nunca omisión silenciosa

`EmployeePersonalData` es una relación opcional por empleado (`personalData
EmployeePersonalData?`). Si un empleado con una liquidación exportable no tiene ese
registro (o le faltan tanto `primerApellido` como `nombres`), no hay ninguna fuente
confiable de nombre para armar la fila. Se evaluaron dos alternativas para el valor de la
fila en sí: (a) incluirla con campos de nombre vacíos, o (b) partir
`EmployeeDetails.name` con un heurístico. Ambas se descartaron — (a) porque un archivo de
consignación con una fila sin nombre es inútil/riesgoso de enviar tal cual a una entidad
externa, (b) por la misma razón de §26.4 (no inventar particiones de nombre).

**Revisado explícitamente antes del commit — comportamiento ante empleados inválidos**:
se evaluaron las dos alternativas señaladas en la revisión (fallar toda la exportación
vs. exportar los válidos reportando los excluidos) y se eligió la segunda, por consistencia
con el precedente ya establecido en `CesantiasService.calculateForYear` (fase 2), que
tampoco aborta un lote completo por un solo empleado con datos insuficientes —
acumula razones de omisión (`CesantiasSkippedEmployee`) y continúa. Fallar toda la
exportación bloquearía la consignación a tiempo de empleados con datos completos por un
problema de datos de un tercero ajeno a ellos — peor resultado operacional para un
archivo con implicación de plazos legales.

**La omisión nunca es silenciosa — implementado en tres capas, no solo documentado**:

1. **Resultado del servicio** — `CesantiasExportFileResult.skipped:
CesantiasExportSkippedEmployee[]` (`{ employeeId, reason }`, `reason` hoy solo puede ser
   `'SIN_DATOS_PERSONALES'`), cubierto por tests explícitos en
   `cesantias-export.service.spec.ts` (incluye un caso mixto: empleado válido + inválido
   en el mismo lote → se exporta el válido, se reporta el inválido).
2. **Log de auditoría** — `CesantiasExportService` llama a
   `AuditService.log({ action: AuditAction.EXPORT, entityType: 'CesantiasLiquidation',
entityId: tenantId, actorUserId, payload: { channel, year, rowCount, skipped } })` en
   cada exportación (incluso cuando `skipped` está vacío). **Esto reutiliza
   infraestructura real y ya existente** — corrección sobre §26.1: sí existe un
   precedente de `AuditAction.EXPORT` en el proyecto
   (`AttendanceCollaboratorsService.exportFile`/`emailExport`,
   `src/attendance/service/attendance-collaborators.service.ts`), que no se había
   encontrado en la primera auditoría de esta fase (esa primera auditoría solo revisó
   `ReportsController`, no todo el repo). Se sigue el mismo patrón exacto: `entityType`
   fijo, `entityId: tenantId` (el export cubre muchos empleados, no uno), `payload` con
   el resumen.
3. **Respuesta HTTP** — `CesantiasController.sendFile` agrega el header
   `X-Cesantias-Export-Skipped-Count` (conteo, siempre presente, incluso en 0) a la
   respuesta binaria. Se usa el conteo y no el detalle completo en el header a propósito:
   el detalle completo (con razones) ya vive en el log de auditoría y en el resultado del
   servicio; ponerlo también en un header arriesgaría exceder límites de tamaño de header
   HTTP en tenants con muchas omisiones. El conteo es suficiente señal de que algo se
   excluyó, en cualquier escala.

## 27. Reglas de exportación

- **Solo liquidaciones del tenant del caller** — `CesantiasRepository.findExportableByTenantAndYear(tenantId, year)`, scoping idéntico al resto del módulo.
- **Solo el año solicitado** — mismo parámetro `year` que `calculateForYear`/`listByYear`, validado con el mismo rango (`assertValidYear`, 2000..añoActual+1).
- **Solo estados exportables** — `cesantiasStatus IN (CALCULADA, CONSIGNADA)`. `ANULADA`
  nunca se exporta (filtrado en el repositorio, no en el servicio). No se filtra por
  `interestStatus` porque los intereses no forman parte de este archivo (ver siguiente
  punto).
- **No incluye intereses** — la columna "Valor a Consignar" toma `cesantiasAmount`
  exclusivamente. `interestAmount` nunca se lee para construir las filas.
- **No cambia el estado de la liquidación al exportar** — `CesantiasExportService` solo
  hace lecturas (`findExportableByTenantAndYear`, `findManyWithPersonalDataByIds`); no
  hay ningún `update`/`upsert` en todo el flujo de exportación. Verificado por inspección
  del código y por los tests (ningún mock de escritura se configura ni se invoca).
- **Clasificación por snapshot, no por fondo actual** — el filtro FNA/privado se hace
  sobre `CesantiasLiquidation.fundChannelSnapshot` (el valor fijado en el momento del
  cálculo), nunca sobre `EmployeeDetails.cesantiasFundName` (el fondo actual del
  empleado). Un cambio de fondo posterior al cierre del año no reclasifica una
  liquidación ya calculada — cubierto explícitamente en
  `cesantias-export.service.spec.ts` ("cambio de fondo — usa el snapshot").

  **Verificado explícitamente antes del commit — la clasificación usa el enum
  persistido, no una comparación de texto**: `fundChannelSnapshot` es la columna real
  `CesantiasFundChannel` (Postgres enum: `FNA` | `PRIVATE_OPERATOR`, ver §16 Parte 2) —
  no un string derivado en esta capa. En `CesantiasExportService.generateFile`:
  `liquidations = allExportable.filter((l) => l.fundChannelSnapshot === channel)`, donde
  `channel` llega tipado `CesantiasFundChannel` desde `generateFnaFile`/
  `generatePrivateFundsFile` (`CesantiasFundChannel.FNA` /
  `CesantiasFundChannel.PRIVATE_OPERATOR`). Es una comparación enum-contra-enum.
  **Distinción importante, ya documentada en §16.6**: ESE valor de enum se deriva, en
  fase 2 (`CesantiasService.deriveFundChannel`), comparando el **nombre** del fondo
  contra el string exacto `"Fondo Nacional del Ahorro"` — esa comparación por nombre
  ocurre al calcular la liquidación (una sola vez, con el resultado persistido), no en
  cada exportación. La capa de exportación en sí misma nunca compara por nombre; el
  riesgo de la heurística de nombre sigue siendo el de §16.6, no uno nuevo introducido
  aquí.

CONSIGNADA)`.

  empírica (no solo teórica) contra la base de datos de desarrollo local: se activó el
  logging de queries de Prisma (`log: [{ emit: 'event', level: 'query' }]`) y se ejecutó
  la query real (`employeeDetails.findMany({ where: { tenantId, id: { in: ids } },
include: { user: true, personalData: true } })`) con 10 `employeeIds` reales de
  `palos-de-lena` — resultado: **3 queries SQL en total** (1 para `employee_details`, 1
  batched con `WHERE ... IN (...)` para `users`, 1 batched con `WHERE ... IN (...)` para
  `employee_personal_data`), no 21 (que sería el patrón N+1: 1 + 10 + 10). El número de
  queries es constante independientemente de cuántos `employeeIds` se pidan — es el mismo
  comportamiento de batching por relación que ya usa Prisma para
  `findSalaryHistoryByEmployees`/`findFundHistoryByEmployees` (fase 2, mismo patrón `{ in:
employeeIds }}`). Adicionalmente, `CesantiasExportService.generateFile` invoca este
  método **una sola vez por exportación** (fuera de cualquier loop sobre liquidaciones),
  no una vez por empleado.

- **Endpoints** (`CesantiasController`, mismos guards que `/calculate`:
  `@Roles(...PAYROLL_WRITE_ROLES)` — mismo criterio que los endpoints de exportación de
  `ReportsController`, que también usan el rol de escritura pese a ser semánticamente una
  lectura, por la sensibilidad de los datos financieros expuestos):
  - `POST /api/cesantias/export/fna` — body `{ year: number }` → `.xlsx` binario.
  - `POST /api/cesantias/export/private-funds` — body `{ year: number }` → `.xlsx`
    binario.

  Se usó `POST` (no `GET`) para mantener consistencia con el único precedente existente
  de exportación de archivos en el proyecto (`ReportsController`'s
  `payroll/export`/`employees/export`, ambos `POST` con body), en vez de introducir un
  estilo nuevo (`GET` + query params) solo para este módulo.

## 29. Riesgos identificados (fase 3)

- **§26.2** — la estructura del archivo (incluida la columna "Número ID" agregada) no
  está validada contra documentación oficial del FNA ni de ninguna administradora
  privada — confirmado que esa documentación no existe en el proyecto (búsqueda
  exhaustiva repetida antes del commit). Si el formato real difiere, este archivo
  requerirá ajustes antes de poder usarse en producción para consignar.
- **§26.3.1** — "Salario Mensual($)" (`calculationBase`) puede incluir el auxilio de
  transporte cuando aplicó; no existe en el modelo un campo separado de "solo salario
  base". Si el formato real del FNA exige el salario sin auxilio, este valor no lo
  refleja correctamente hoy.
- **§26.4** — "Segundo Nombre" queda siempre vacío por falta de una fuente de dato
  separada — confirmado mediante búsqueda exhaustiva que no existe en ningún lugar del
  proyecto para el propio empleado (sí existe para beneficiarios, una persona distinta).
- **§16.6 (Parte 2)** — sigue aplicando, sin cambios por esta revisión: la clasificación
  FNA/privado depende de una heurística de comparación exacta de nombre de fondo al
  momento de CALCULAR la liquidación (fase 2), no de un dato de catálogo real; cualquier
  imprecisión ahí se propaga a en qué archivo termina cada liquidación. La capa de
  EXPORTACIÓN en sí (fase 3) no compara por nombre — usa el enum ya persistido (ver
  §27, verificado explícitamente).
